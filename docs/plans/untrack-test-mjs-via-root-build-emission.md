## Goal

One end state, landed in a single workstream (no interim half-fixes):

- **No test `.res.mjs` tracked anywhere in this repo** (254 today → 0).
- **Every package's test outputs are regenerated by one build command run from the repo
  root** (`pnpm run build`) — no per-package `cd`, no CI-only build step.
- **A single `.gitignore` rule** (`**/tests/**/*.res.mjs`) makes them ephemeral; `git status`
  is never polluted by a build again.
- **Every package's tests run in CI**, enforced by `check-jest-projects.mjs` with an empty
  `KNOWN_EMPTY`. This closes the dark-coverage gap (core 518, spec 103, interop 50 tests).

### Hard requirement driving the mechanism

**All packages must compile from the repo root with one command.** `pnpm run build` is already
a single command that chains several `rescript build` invocations (the three example
`platform-local` builds). Option C appends three more to that chain, so the requirement holds:
one `pnpm run build` compiles the whole graph including every test source. (A CI-only
per-package build step would fail this and is rejected. `pinned-dependencies` — which would
have done it in one invocation — no longer exists in the toolchain; see Appendix B.)

## The two classes of package (why only three need a mechanism change)

Measured from a clean root build (verified in the spike, Appendix B):

| Class | Packages | `tests` typing | Root build emits test mjs? | Work needed |
|---|---|---|---|---|
| **A — already emitted** | `reventless/local`, `reventless/aws`, `reventless/gwt`, `examples/*` | plain source (not `dev`) | ✅ yes (local 111, aws 39, gwt 22, examples 158 on disk after a clean root build) | untrack + gitignore + **verify only** |
| **B — skipped** | `reventless/core`, `reventless/spec`, `reventless/interop` | `{"type":"dev"}` | ❌ no (dependency `dev` sources are skipped) | **Option C** — build each as its own root, then untrack + gitignore |

Class A is tracked **redundantly** — the root build already produces those outputs, so
untracking them is safe once a clean build confirms they reappear. Only Class B needs the
build-script change. This is the core insight that de-risks the bulk of the sweep.

## The mechanism — Option C (root-build-script variant)

Building a package **as its own build root** (`rescript build reventless/core`) emits its
`type: dev` test sources in-source — verified in the spike (core 69, spec 10, interop 3), with
`type: dev` kept. So append the three Class-B packages to the root `build` script:

```jsonc
// package.json — root "build", spec before core (dependency order)
"build": "rescript build \
  && rescript build examples/online-shop-aggregates/platform-local \
  && rescript build examples/online-shop-dcb/platform-local \
  && rescript build examples/online-shop-hybrid/platform-local \
  && rescript build reventless/spec \
  && rescript build reventless/core \
  && rescript build reventless/interop"
```

- **Keeps `type: dev`** → no change to what a published-package consumer compiles → **no
  release-mode regression risk**.
- **Satisfies compile-from-root** → still one `pnpm run build`.
- **Minimal surface** → only `package.json` changes; no `rescript.json` / published-package
  semantics touched.

## Companion note — `rescript-legacy` is a *targeted* fallback, not a blanket switch

The **rescript@12.3.0 rewatch UTF-8 panic** (`compile.rs:791`, see
`docs/fixes/rescript-rewatch-utf8-stdout-panic.md`) fires only on a build that emits a
warning/error whose quoted source context has a non-ASCII char at a read-buffer boundary. Core
builds clean at 12.3.0 today, and Option C's appended per-package builds newly compile the
`type: dev` **test** sources — where non-ASCII lives (em-dashes / box-drawing in GWT
descriptions) — so a Class-B build *could* trip the panic. **Use `rescript build` (rewatch)
normally; only if one of the appended per-package builds actually panics, switch that single
invocation to `rescript-legacy build`** (the ninja path — immune; `console-web` already uses
it). `rescript-legacy` ships inside ReScript 12 as a supported escape hatch and drives the same
`bsc` compiler, so it is not abandoning v12 — it's a per-invocation mitigation until the
upstream one-line `from_utf8_lossy` fix lands (drafted in the fixes doc; still worth filing).

## Phase 2 — Untrack every test `.res.mjs` (Class A + B together)

Do this only after Phase 1 is green locally.

1. Add one rule to the root `.gitignore`:
   ```gitignore
   # Test outputs are regenerated by every root `pnpm run build` (Class-A packages
   # in-source; Class-B via the appended per-package `rescript build`), so never tracked.
   **/tests/**/*.res.mjs
   ```
2. Remove the now-redundant lone per-package rule `rescript/effect/.gitignore`
   (`tests/*.res.mjs`) — the root rule subsumes it.
3. Untrack the tracked outputs without deleting them from disk:
   ```bash
   git ls-files '*/tests/*.res.mjs' -z | xargs -0 git rm --cached --quiet
   ```
   Expect ~254 removals across local/aws/gwt/examples (core/spec/interop were never tracked).
4. **Verify the round-trip on a clean tree:** `rm -rf **/lib **/tests/**/*.res.mjs`, then
   `pnpm run build` → `git status` must be **clean** (every test mjs regenerated and ignored),
   and `pnpm test` must discover the same suite count as Phase 1.
   - **Guard the entry points:** the clean step deletes two tracked
     `examples/*/platform-aws/src/Main.res.mjs` (observed in the spike). Restore with
     `git checkout HEAD -- <path>` — do **not** rebuild — and confirm the final `git status`
     shows them present/unchanged.

## Phase 3 — Enforce & document

1. Empty `KNOWN_EMPTY` in `scripts/check-jest-projects.mjs` (remove `reventless-core`,
   `reventless-interop`; spec is now a real project). The guard now enforces **every** project.
2. Update `CLAUDE.md` §`.res.mjs` tracking: test outputs move from **Tracked** to **Not

3. Update `ci.yml` affected-path handling if needed so a change under any `tests/` dir still

## Risks & mitigations

- **A Class-B build panics** (rewatch UTF-8 bug on a non-ASCII test warning). *Mitigation:*
  switch that one invocation to `rescript-legacy build` (companion note above). Targeted, cheap.
- **The clean step deletes tracked example entry points.** *Mitigation:* Phase 2 step 4 restores
  them via `git checkout` and the final `git status` check catches any miss.
- **Build wall-clock** — three extra per-package builds. *Mitigation:* they're small packages;
  the aws slice showed adding suites did not regress warm-cache wall-clock.
- **A silent CI coverage drop** if a `tests/` dir stops emitting. *Mitigation:* that is exactly
  what `check-jest-projects.mjs` now fails on.

## Non-goals

- `src/` mjs and `examples/**/Main.res.mjs` entry-point tracking — consumed artifacts, stay
  tracked (CLAUDE.md).
- Publishing / release-mode consumer behavior — untouched, because `type: dev` stays.
- Cross-repo linking (separate analysis).

## Appendix A — Rejected alternative: drop `type: dev`

Removing `{"type":"dev"}` from `reventless/{core,spec,interop}/rescript.json` would make their
test dirs plain sources the *single* root `rescript build` already emits (like Class A) — a
simpler build script. **Rejected as the default** because `type: dev` on `spec` was added
deliberately to keep `tests/` (and its `rescript-jest` devDependency) out of release-mode
consumer builds; dropping it risks a consumer-build regression and would require running that
cross-repo release-mode gate first (prior evidence says it likely regresses). Option C avoids
the question entirely by keeping `type: dev`. Revisit only if the appended per-package builds
prove more trouble than the flag.

## Appendix B — Phase 0 spike record — NO-GO on `pinned-dependencies` (2026-07-25)

The spike ran on the working tree (working branch, tree restored to baseline afterward).
The go/no-go criterion failed: **`pinned-dependencies` does not emit Class-B test outputs
because the field no longer exists in the toolchain.**

### What the spike found

Toolchain: **ReScript v12.3.0**, whose default build system is **rewatch**
(`rescript build` = rewatch; the pre-v12 bsb build is now `rescript-legacy`).
`pnpm run build` → `rescript build`.

1. Added a `pinned-dependencies` block to the root `rescript.json`, wiped every
   non-`node_modules` `lib/`, and ran `pnpm run build` from a clean state. Result:
   ```
   Unknown field 'pinned-dependencies' found in the package config of
   'reventless-monorepo'. This option will be ignored.
   ```
   Class-B test mjs on disk afterward: **core 0, spec 0, interop 0.**
2. The rewatch binary (`@rescript/darwin-arm64/bin/rescript.exe`) contains **no `pinned`
   string at all**. `node_modules/rescript/CHANGELOG.md` records the cause:
   > Remove all leftovers of `pinned-dependencies` handling. (PR rescript-lang/rescript#7686)

   `pinned-dependencies` was **removed from ReScript v12**. This is not a config error;
   the mechanism the plan was originally built on is gone from the compiler. (Consistent with
   repo history: commit `41c87da58`, the v12.1/rewatch migration, stripped the field.)

### What *does* work (verified in the same spike, tree since restored)

| Mechanism | Result |
|---|---|
| Class-A tests (plain source, no `type: dev`) via root `rescript build` | ✅ emit in-source (local 111, aws 39, gwt 22, examples 158) — confirms Class-A can be untracked |
| Class-B tests via `pinned-dependencies` | ❌ field ignored, 0 emitted |
| **Class-B via `rescript build reventless/<pkg>` (build the package as its own root)** | ✅ emits `type: dev` tests **in-source** (core 69, spec 10, interop 3) with the flag kept → **this is Option C** |

Gotcha observed: rewatch skips **re-emitting** an in-source `.res.mjs` when `lib/bs`
already holds the artifact (incremental cache). A clean build (`rm -rf lib`) emits
in-source correctly; the CI enforcement point is a fresh checkout, so this is a local-
only wrinkle, not a CI risk. Also: rewatch's clean step removed two tracked
`examples/*/platform-aws/src/Main.res.mjs` entry points during the spike — the sweep must
`git checkout`-restore them (Phase 2 step 4).

### Decision

**Option C** (root-build-script variant), confirmed by the owner 2026-07-25 over the
drop-`type: dev` alternative (Appendix A) — Option C keeps `type: dev`, was proven in this
spike, carries no release-mode consumer risk, and touches the least surface.

## Appendix C — Background & prior work (folded from the archived coverage-gap plan)

Everything needed to execute is above; this preserves the diagnosis and history so this plan
stands alone. Full detail (incl. diagnostic war-stories) remains in the archived
`docs/plans/ci-unit-test-coverage-gap.md`.

**How the gap was found (2026-07-22).** While verifying a rename, `CommandAuthorizationTest`
and `Auth_CognitoTest` couldn't be run via root `pnpm test` — they exist and pass, CI just
never ran them. That surfaced a whole class of **dark coverage**: green when run directly,
never executed in CI.

**The dark-coverage measurement:**

| Package | `*Test.res` | Ran in CI before? | Measured |
|---|---|---|---|
| local | 73 | ✅ | — |
| gwt | 14 | ✅ | — |
| aws | 28 | ✅ **wired up 2026-07-22** | 21 suites / 280 tests (7 integration excluded by design) |
| **core** | 49 | ❌ | 49 suites / **518 tests** pass |
| **spec** | 10 | ❌ | 10 suites / **103 tests** pass |
| **interop** | 3 | ❌ | 3 suites / **50 tests** pass |

Remaining gap this plan closes: **62 suites / 671 tests**, including all of framework core.

**aws slice — DONE (2026-07-22), reused here.** aws was separable (its test outputs are
tracked + present in a fresh clone; it lacked only a jest project). Root `pnpm test` went
169→190 suites, 1113→1393 tests. Added a `reventless-aws` jest project carrying the package's
`testPathIgnorePatterns` (so `tests/integration/` + `Pg.*IntegrationTest` stay owned by
`test:integration`/`test:integration:pg`, no double-run), used the **root** `jest.setup.cjs`
(superset — its `structuredClone` polyfill keeps DynamoDB `TransactionCanceledException` detail
unmasked), and added CI affected-path mappings for `reventless/aws/` + `reventless/gwt/`.

**Why core/spec/interop are dark (Cause 1 & 2).** Their `rescript.json` marks `tests` as
`{"type":"dev"}`; the root build (packages as `dependencies`, `sources: []`) **skips dependency
`dev` sources** and its clean step removes any a prior per-package build emitted → 0 test mjs on
disk → jest matches 0 files → **exits 0 (silent pass)**. Additionally `spec` has **no jest
project** at all. (Confirmed: `cd reventless/core && pnpm run build` emits 49 outputs; a
subsequent root build removes them; survives a clean `pnpm install --frozen-lockfile`.)

**The guard — DONE (2026-07-22), acceptance harness here.** `scripts/check-jest-projects.mjs`
(`pnpm run test:projects`, a CI step gated on a successful build) **fails if any declared jest
project discovers 0 suites** — closing the silent-pass hole. A total-count assertion was
rejected as brittle; per-project ≥1-suite is robust to test growth. `reventless-core` +
`reventless-interop` sit in `KNOWN_EMPTY`; the check *also* fails if a listed project starts
finding suites, forcing the list to shrink as this plan lands (Phase 3 empties it).

**Why not the other decision options.** **Option A (drop `type: dev`)** → see Appendix A
(release-mode consumer risk; rejected as default). **Option B (track the test mjs for
core/spec/interop, like local/aws/gwt)** → rejected: the root build's clean step deletes them,
so every build leaves tracked *deletions* in the tree (hit twice during the Admin rename). Not
viable. **Option C** avoids both.

**Gotchas worth keeping** (cost time before): (a) the repo's custom jest reporter can swallow
the real error and print a misleading `(0 tests)` PASS — use `--reporters=default` to see the
actual cause; (b) `git stash` to prove a failure is "pre-existing" only rules out *source*
causes — it leaves `node_modules` untouched (a missing-`node_modules` install gap in two hybrid
example packages once masqueraded as a test failure; `pnpm install --frozen-lockfile` fixed it,
lockfile untouched, CI never affected).

**Unverified (carry into execution):** whether adding ~62 suites materially changes CI
wall-clock — the aws slice added 21 suites and the warm-cache full run got *faster*, so the
expected cost is the extra build invocations, not the tests.
