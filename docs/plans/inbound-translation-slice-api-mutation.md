# Plan: InboundTranslationSlice — Auto-Expose as GraphQL Mutation

Auto-generate a GraphQL mutation endpoint for each `InboundTranslationSlice`, so the framework provisions the full path from HTTP to domain command with zero manual wiring.

See `docs/analysis/inbound-translation-slice-trigger-specification.md` for the analysis behind this decision (Alternative A).

**Branch**: feature/inbound-translation-api-mutation (from alpha)

---

## Context

Today, `InboundTranslationSlice` exposes `operations.receive(JSON.t)` but nothing connects it to an external entry point. StateChangeSlice mutations are exposed via:

1. **Schema generation** — `Plugin_Builder` builds `mutationSchemaEntry` per slice using `commandSchema`
2. **Fragment generation** — `GraphQL_FragmentGenerator` derives SDL mutation fields from the schema
3. **Resolver hook** — `dcbMutationResolverHook` registers GraphQL resolvers per slice (in-memory platform)
4. **AWS resolvers** — AppSync `Resolver` + `DataSource` pointing to the DCB CommandTopic Lambda

InboundTranslationSlice follows a **different runtime path**: it does not route through CommandTopic handlers. It calls `receive(inputJson)` directly, which internally parses, translates, and publishes. The resolver must call `receive` — not dispatch to a CommandTopic handler.

## Step 4: Implement in-memory resolver for InboundTranslationSlice

**New file**: `reventless/reventless-in-memory/src/adapter/CommandGenerator/InboundTranslationResolvers_GraphQL.res`

This is the in-memory platform's implementation of the resolver hook. Unlike `DcbCommandTopicResolvers_GraphQL` (which routes through CommandTopic handlers), this resolver calls `receive` directly:

```rescript
@@warning("-44")
open ReventlessCore

let register = (
  ~fieldName: string,
  ~externalInputSchema: S.t<unknown>,
  ~receive: JSON.t => promise<result<string, string>>,
) => {
  // Derive SDL from externalInput schema
  let sdlFields = switch GraphQL_FragmentGenerator.deriveMutationFieldFromObject(
    ~fieldName,
    externalInputSchema,
    ~authorization=None,
  ) {
  | Some(field) => [field]
  | None => [`  ${fieldName}: String!`]
  }

  let resolver: GraphQL_Server.resolverFn = async (_root, args) => {
    // Pass args directly as JSON to receive — it handles parsing via externalInputSchema
    let inputJson = args->Obj.magic
    let result = await receive(inputJson)
    switch result {
    | Ok(targetId) => targetId->JSON.Encode.string
    | Error(msg) => msg->JSON.Encode.string
    }
  }

  let resolvers = Dict.make()
  resolvers->Dict.set(fieldName, resolver)
  GraphQL_Server.registerMutations(~sdlFields, ~resolvers)
}
```

Key simplification vs DCB resolver: no TAG extraction, no command body construction, no CommandTopic routing. The `receive` function already handles parsing, validation, translation, and command publishing internally.

## Step 6: AWS platform — AppSync resolver for InboundTranslationSlice

**Context**: On AWS, the InboundTranslationSlice runs in its own Lambda (or shares the DCB Lambda). The AppSync resolver invokes this Lambda with the mutation arguments as the event payload.

This step requires understanding how the InboundTranslationSlice Lambda is currently deployed (or if it needs a new Lambda). Two sub-approaches:

### Option A: Reuse DCB CommandTopic Lambda

Add a routing branch in the DCB CommandTopic Lambda handler that recognizes InboundTranslationSlice field names and calls `receive` instead of routing through CommandTopic handlers. This keeps the Lambda count the same but adds complexity to the handler.

### Option B: Dedicated Lambda per InboundTranslationSlice

Create a separate Lambda + AppSync DataSource + Resolver for each InboundTranslationSlice. Simpler routing but more infrastructure resources.

**Decision**: Defer to implementation time — analyze the AWS DCB runtime handler to determine which option fits better. The in-memory implementation (Steps 1-5) validates the schema generation and resolver pattern first.

## Design Decisions

1. **`externalInputSchema` as mutation arguments** — The external input type defines the GraphQL arguments, not the internal command type. This preserves the anti-corruption boundary: the API speaks the external vocabulary, the slice translates internally.

2. **Separate hook from `dcbMutationResolverHook`** — The InboundTranslationSlice resolver calls `receive` directly. Reusing the DCB hook would force the resolver to build a command body and route through CommandTopic, which bypasses the translate/audit logic in the Callback.

3. **`receive` captures the full pipeline** — The resolver doesn't need to know about command encoding, publishJsons, or audit logging. It calls `receive(json)` and gets back `result<string, string>`. All internal plumbing is encapsulated.

4. **No spec changes** — The existing `@schema type externalInput` already provides everything needed for schema generation. The mutation is derived entirely from what the spec already declares.
