# Plan: say how to write a value of every semantic type

**Status:** 🚧 V1 built — 2026-09-22. `Semantic.valueTypes`, a `sample` on every branded
string, and `tests/SemanticValueTypesTest.res`; where the sources differed from this plan, see
[What V1 found](#what-v1-found). Not yet released (V2).<br/>
**Touches:** `reventless/spec/src/semantic/Semantic.res` and a test beside
`tests/SemanticBrandedStringsTest.res`. No PPX change, no runtime change.<br/>
**Consumer:** reventless-tools' scenario form, which fills every field of a new scenario with
a value that compiles, and offers an input fitting each field's type (reventless-tools
`docs/plans/scenario-example-data.md`, phases E1b and E3). Sequenced there by
`docs/plans/scenario-authoring-orchestrator.md`.

## Goal

A tool can ask the framework, for any semantic type a field may carry, **how to write a
value**, what a **sensible sample** is, and **what input** fits it. The tool never has to
transcribe the set or guess from type names.

## Why

`Semantic.brandedStrings` already answers this for the transparent-string semantics
(`DateTime`, `Email`, `Url`, …): a string literal is a value. Its test recomputes the list
from the sources, so it cannot drift.

The remaining semantics have no such answer:

| Module | `type t` | How a value is written today |
|---|---|---|
| `Money` | record | `Money.make(~amount, ~currency)` |
| `Currency` | closed code set | a constructor (`EUR`); `Currency.all` lists them |
| `DateRange` | record | `{start, end_}` (`make` validates and returns `result`) |
| `GeoPoint` | record | `{lat, lng}` (`make` validates and returns `result`) |
| `CaptionedImage` | record | a record literal |
| `Duration` | `int` | an int literal |
| `Percent`, `Bytes` | `float` | a float literal |

The type names cannot say it: `Money.t` is a record, `Duration.t` an int. That is the same
reason `brandedStrings` exists. A tool that guesses writes code that does not compile. The
scenario form today treats all of these as "type the ReScript yourself", and that is the
error a user meets on the first open of the form.

## Design

Add one list next to `brandedStrings`, and a sample to each branded string.

```rescript
type valueShape =
  | Number({integer: bool})                    // Duration, Percent, Bytes
  | Codes({codes: array<string>})              // Currency: from `Currency.all`
  | Parts({parts: array<(string, string)>})    // Money, DateRange, GeoPoint, CaptionedImage: (part, module or primitive)

type valueType = {
  moduleName: string,
  shape: valueShape,
  /** A value, written as ReScript source, fully qualified: what a tool emits. */
  sample: string,
  /** How to write one from its parts: `Reventless.Money.make(~amount=$amount, ~currency=$currency)`,
      or a record literal `{lat: $lat, lng: $lng}`. `$part` is replaced by the part's source. */
  writer: string,
}

let valueTypes: array<valueType>
```

- **`brandedString` gains `sample: string`** (for example `"2024-01-01T00:00:00Z"` for
  `DateTime`, `"ada@example.com"` for `Email`). It must be a value the module's own schema
  accepts, because a tool will write it into tests that decode it.
- **Samples are valid values.** Where the module has a validating constructor
  (`DateRange.make`, `GeoPoint.make`), the test runs the sample through it.
- **The writer uses the module's own spelling:** the constructor where it returns `t`
  (`Money.make`), and the record literal where the constructor returns `result` (a test value
  should not need unwrapping).
- **Infrastructure modules are not values.** `Capabilities`, `CapabilityNeed`, `Geolocation`,
  `IdentityProvider`, `Secrets`, `Template`, `Semantic` and the like live in `semantic/` but
  never type a field a scenario fills. They are listed once, as such, so the test can tell a
  forgotten module from a deliberate omission.

## Phases

### V1 — The list and its test

- `valueTypes` for the seven modules above, and `sample` on every `brandedString`.
- A test in the spirit of `SemanticBrandedStringsTest`:
  - **Coverage:** every `semantic/*.res` module is exactly one of: a branded string, a value
    type, or a listed non-value module. A new module fails the test until it is classified.
  - **Samples decode:** each sample, parsed through the module's schema, is accepted.
  - **Writers compile:** each `writer` with the sample's parts substituted is compiled in a
    fixture file (the test file itself can hold one `let` per type, generated by hand once and
    checked against the list).
  - **Codes are the module's:** `Currency`'s codes equal `Currency.all->Array.map(toString)`.

### What V1 found

The sources differed from the plan in these places. V1 follows the sources.

- **`Money`'s amount is whole minor units**, held in a `float`: `make(~amount=1000.0, ~currency=EUR)`
  is 10.00 EUR. The sample is exactly that. The tools plan's E1b example `~amount=10.0` would
  be 0.10 EUR.
- **`CaptionedImage` has no `schema`.** Its schema is `forField(~plugin?, ~store)`, and its
  record is `{ref: UploadableImage.t, altText?: string, caption?: string}`. The writer fills
  all three parts; the test decodes the sample through `forField(~store="example")`.
- **`DateRange`'s end field is `end_`** in source (`end` on the wire), so the writer is
  `{Reventless.DateRange.start: $start, end_: $end_}`.
- **`Geolocation` does type a field a scenario fills.** The hybrid shop's `Customers` view
  holds `geolocation: Reventless.Geolocation.t`, and `Customers_GWT` asserts it. It is a union
  of cases with payloads, which `valueShape` cannot express. It is listed on its own, in
  `Semantic.valueTypesWithoutWriter`, rather than as infrastructure. A tool asks for its value
  as ReScript source until a shape for unions is designed.
- **The non-value modules** are `Capabilities`, `CapabilityNeed`, `Geocoding`,
  `IdentityProvider`, `Media_Ref`, `Messaging`, `Offload`, `RowImage`, `Secrets`, `Semantic`
  and `Template` (`Semantic.nonValueModules`).
- **The single-part writers** name their part: `$value` for a `Number` and `$code` for a
  `Codes` (`Reventless.Currency.$code`).
- **The branded-string `sample` is the string itself**, not its source; a tool writes it as a
  string literal. For the modules whose schema takes a store or collection, the test checks
  the sample against a schema built for `"example"`, and also against `fromString` where the
  module has one.

### V2 — Release

- A normal core release; the spec package carries it. It may ship in the same release as the
  PPX's scenario-id marker (`docs/plans/scenario-id-marker.md`); neither depends on the other.

## Out of scope

- **`Reventless.Lifecycle.Trail.t`** and other framework types outside `semantic/`. A trail is
  derived by a projection and written in tests through a helper. Whether tools should offer a
  writer for it is a separate question, raised once the scenario form meets one it cannot
  write.
- **The PPX's own copy of the branded-string set** (`Util.branded_string_modules`) is
  untouched. It does not need samples.

## Risks

- **Samples that look like data.** A sample becomes the value a new scenario starts with. It
  should read as an example (`10.00 EUR`, `ada@example.com`) and never as something a person
  might mistake for real data.
